# Catalog qualification authoring and adjudication protocol

Qualification is authored in stages. No proposal, review page, reviewed description set, query
draft, candidate pool, or status field authorizes model execution. An executable qualification
fixture is created only after every answer-key surface has an exact creator decision artifact.

## 1. Evidence audit and development description pilot

Audit every source-name observation before selecting review assets. An explicit `_Collision`
suffix identifies a non-renderable collision companion only. Exclude it from appearance review and
report any measurement that classifies it as renderable. Materials attached to its source geometry
are diagnostic input, not evidence that the collision shell should be textured or rendered.

Select exactly 24 deliberately varied assets whose complete leakage groups belong to the
development split. Do not expose calibration or evaluation assets. Internal selection tags are
multi-valued, non-authoritative, and reuse the existing visual-composition, source-role, and
completeness vocabulary alongside pilot-only boundary, source-name, style, and vegetation coverage.
They select a varied cohort; they are not fields in the creator decision.

Inspect all twelve RGB views and the exact metric summary. The required creator decision asks only
whether the proposed text accurately describes visible form, appearance, and composition. Choose
`accurate`, `edited`, `unsure`, or `image_problem`. An edited answer supplies a corrected concrete
description; unsure supplies a broad supported description plus the unresolved visual uncertainty;
image problem records typed defective evidence and makes the description unreviewable. Contextual
use, assembly purpose, completeness, and sampling categories are not approved by this decision.
Generic completions such as `object`, `object aggregate`, `modular piece`, or `stylized asset` are
invalid.

Filename observations remain in a visually separated disclosure with authority `none`. They may
help a reviewer notice a mismatch but never decide the description. Proposal generation is
unscored review assistance and must remain separate from qualification results.

The creator decision binds the exact proposal hash and every asset identity. An `accurate` action
means the proposed evidence usability and visible-description assessment are byte-for-byte
unchanged. Internal selection tags never enter the decision or reviewed description set. The sealed
description set binds the hash and full contents of that decision and still records
`qualificationExecutionAuthorized: false`.

## 2. Query authoring

Begin only after the development description pilot is creator reviewed and judged useful. Author
distinct realistic asset requests rather than transforming descriptions mechanically. Cover
appearance, metric dimensions, whole-versus-component distinctions, close visual alternatives,
true no-match cases, and properties the available evidence cannot establish. Never derive query
text, relevance, or confusers from noun equality.

## 3. Retrieval pooling and relevance review

Run every retrieval method being compared only to form candidate pools. For each query, take the
canonical union of those results. In the mixed scenario, retain relevant background assets as
judgeable candidates; cohort membership cannot limit relevance credit.

Independently review every pooled query–asset relationship against visual and measured evidence.
Use `relevant`, `irrelevant`, or `unknown`. Unknown remains outside positive and negative scoring;
it is never silently converted to an error. Bind the reviewed decision to the exact query text,
constraints, pool membership, candidate identity, and evidence hashes.

## 4. Validator cases and execution gate

Create validator cases only from the reviewed queries and candidates. Independently adjudicate the
expected validator verdict. Match and mismatch require available evidence; an unavailable property
must remain uncertain rather than becoming a no-match.

Generate the executable development, model-selection, and holdout packets only after query,
relevance, and validator review is complete. Preserve whole leakage groups and the existing holdout
procedure. Freeze prompts, schemas, models, worker implementation, and thresholds before the single
holdout run. The runner must load and verify every referenced creator decision artifact and compare
its contents with the final answer key. Editing status or provenance fields cannot unlock
execution.
